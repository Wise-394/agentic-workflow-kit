# Agentic Workflow Kit — Design

Date: 2026-11-18
Status: Draft, awaiting review

## 1. Goal

A reusable, tool-agnostic and model-agnostic kit for running a team of coding agents on any repository. The user points an agent at this repo ("read github.com/<owner>/agentic-workflow-kit and set it up here"); the agent detects what it can, asks the rest, and writes the project's configuration. Work state lives in the issue tracker, not in repo files.

### Non-goals

- No installer program. The kit is markdown that an agent follows.
- No hard-coded tool, model, stack, or tracker in kit files.
- No picking work on its own initiative. The user starts either one issue (`run-issue`) or a whole milestone (`run-sprint`).

## 2. Principles

1. **Stateless.** Any agent on any machine can resume a ticket from the tracker (issue, labels, plan comment, branch, PR).
2. **Prove it works.** No success claim without evidence: command output, test results, logs, screenshots, or a checklist the user answered.
3. **Ask, don't guess.** Product, data, API, library and architecture decisions that the issue, plan, and docs don't answer go to the user.
4. **Independent review.** The PR reviewer never sees the builder's reasoning; it gets only the issue and the diff.
5. **Copy, then update on request.** Projects hold readable copies of kit files and a lock file; updates are explicit and diffed.

## 3. Kit repository layout

```
agentic-workflow-kit/
  README.md          what the kit is, how to install, how to update
  SETUP.md           agent-run install: detect → confirm → ask → preview → write → verify
  UPDATE.md          agent-run update: compare lock version, show diff, keep answers and local edits
  CHANGELOG.md
  VERSION
  roles/             one file per role: purpose, inputs, outputs, allowed actions, stop conditions
    planner.md  scout.md  test-writer.md  coder.md  checker.md  verifier.md  delivery.md  pr-reviewer.md
  skills/            portable SKILL.md files
    run-issue/       one issue, issue → PR (section 6)
    run-sprint/      a whole milestone on a sprint branch (section 7)
    write-plan/      plan comment structure and rules
    playbooks/       feature, bug-fix, refactor, investigation
    verify/          how to create and maintain a project's verify-<project> skill
    pr-review/       independent PR review incl. blast radius
    plan-project/    idea → PRD → milestones → issues (incl. one verification issue per milestone); update mode
  tracker/
    github.md        exact gh commands for every tracker action (section 9)
  templates/
    AGENTS.md        project rules skeleton
    issue.md  plan-comment.md  pr-body.md  verification-issue.md
    docs/testing.md  docs/patterns.md  docs/clean-code.md
    lock.json
  adapters/          how to render roles, models and permissions for a specific tool
    opencode.md  claude-code.md
  safety/
    baseline.md      the universal rules (section 10)
  examples/sandbox/  tiny repo used to test the kit
  docs/specs/        design documents
```

Kit files never name a model, tool, stack, or project. Adapters are the only files that know a tool's config syntax; adding a tool means adding one adapter file.

## 4. What a project holds after setup

- `AGENTS.md` — project rules (new, or merged into the existing file with user approval).
- Tool-specific agent files generated by the adapter (e.g. `.opencode/agents/*.md` + `opencode.json`, or `.claude/agents/*.md` + `.claude/settings.json`). Permissions written once at the global/project level, plus per-role differences only.
- Copies of the kit skills the project uses.
- `docs/testing.md`, `docs/patterns.md`, `docs/clean-code.md` starters, filled from the repo where possible.
- A generated `verify-<project>` skill.
- `.agentkit/lock.json`:

```json
{
  "kitVersion": "0.1.0",
  "tool": "opencode",
  "models": { "thinking": "<provider/model>", "working": "<provider/model or inherit>" },
  "commands": { "check": "npm run check", "test": "npm test -- {file}", "format": "npm run format" },
  "forbiddenCommands": ["expo prebuild", "gradlew"],
  "git": { "integrationBranch": "dev", "branchPattern": "<type>/<issue>-<slug>", "sprintBranchPattern": "sprint/<milestone>" },
  "tracker": { "kind": "github", "repo": "<owner>/<repo>" },
  "merge": "user",
  "limits": { "sameErrorRetries": 8 },
  "localEdits": []
}
```

No sprint, timeline, status, or plan files in the repo.

## 5. Setup flow (`SETUP.md`)

1. **Detect** without asking: tool in use and existing agent config; stack and commands (package.json, Makefile, pyproject, …); default and integration branches and branch naming; tracker remote and `gh auth status`; existing rules and docs.
2. **Confirm.** Show findings in one message; the user corrects.
3. **Ask** only what is missing, one question at a time, plain words with examples:
   - Model for the *thinking* group (planner, pr-reviewer) and the *working* group (scout, test-writer, coder, checker, verifier, delivery). Default: inherit the session model.
   - Forbidden commands (stack-based suggestions offered).
   - Merge policy: `user` or `agent`.
   - Label and milestone naming (defaults offered).
4. **Preview.** List every file to create or change and every label/board to create. Wait for yes.
5. **Write** files through the adapter; create labels and board with `tracker/github.md` commands; write `lock.json`.
6. **Verify** with a checklist: files exist, tool loads the agent config, check command runs, `gh label list` shows the labels, verify skill exists. Report pass/fail per row.
7. **Offer next step:** `plan-project` (idea → issues) or import existing work.

Failure handling: stop and ask on missing `gh` login, undetectable check command, or an existing file it doesn't understand. Never overwrite a file it didn't create without showing the diff.

## 6. Running an issue (`skills/run-issue`)

1. **Intake.** User pastes an issue link or number. Read body, all comments (newest can override), and linked issues. Choose a playbook: feature, bug-fix, refactor, or investigation. Add `status:in-progress`, assign.
2. **Plan.** Planner writes scout questions; scout answers from code and docs. Planner posts the **plan comment**: playbook, contracts (files, exports, shapes), every test in plain words (setup / action / expect / fails-first-because), steps in build order, files allowed, *proof plan* (tests + verify-skill checks), user checks, decision log. Open questions go in one comment mentioning the user; label `status:needs-input`; stop until answered.
3. **Branch.** Delivery creates `<type>/<issue>-<slug>` from the integration branch.
4. **Build.** Test-writer writes the planned tests and shows each failing for the stated reason. Coder makes them pass. Checker runs the check command. Workers fix their own failures up to the retry limit; plan changes go back to the planner.
5. **Verify.** Verifier runs the project's `verify-<project>` skill and collects evidence. Checks an agent may not run (e.g. building a phone app) become a user checklist.
6. **PR.** Delivery opens the PR: summary, tests added, check results, evidence, remaining user checks, `Closes #N`, link to plan comment. Label `status:in-review`.
7. **Independent review.** A fresh pr-reviewer gets only the issue and the PR diff. It checks requirements, tests (no weakened assertions), invariants from `AGENTS.md`, scope, and blast radius (callers of changed code). It posts a real GitHub review: approve, or request changes with line comments. Requested changes return to step 4 on the same branch; findings are appended to the plan comment as a checklist; review runs again.
8. **Merge.** Requires: approval, green CI, evidence attached. `merge: agent` → agent merges into the integration branch. `merge: user` → agent reports "approved, ready to merge" and stops. The issue closes via `Closes #N`.

Playbook differences:
- **Bug fix:** reproduce with a failing test first; state the root cause before any fix.
- **Refactor:** behavior unchanged; existing tests must pass untouched; no new behavior tests.
- **Investigation:** no code; output is a findings comment with evidence and a recommendation.

Resume: read labels, plan comment, branch, and PR; continue from the first unfinished step.

When run inside `run-sprint`, the issue branch is cut from the sprint branch, the PR targets the sprint branch, and after approval the agent always merges it there (the merge setting applies only to the final sprint PR).

## 7. Running a sprint (`skills/run-sprint`)

Triggered by the user naming a milestone ("run sprint 2").

1. **Sprint branch.** Create `sprint/<milestone>` from the integration branch. Open a draft PR `sprint/<milestone> → <integration branch>` immediately; it is the live progress view.
2. **Order.** Read the milestone's open issues (excluding its verification issue), sort by "Blocked by" links, show the order to the user once, then start.
3. **Each issue.** Run `run-issue` against the sprint branch (section 6). After independent review approves and CI is green, the agent merges the issue PR into the sprint branch.
4. **Stuck issues.** If an issue needs input or hits a retry/step limit: label it (`status:needs-input` / `status:blocked`), skip to the next issue not depending on it, continue. Dependents of a stuck issue wait.
5. **Sprint verification.** When no runnable issues remain, run the milestone's verification issue against the whole sprint branch: full check command, the `verify-<project>` skill, and the user checklist.
6. **Sprint review.** A fresh pr-reviewer reviews the full sprint PR diff for cross-issue conflicts, duplicated helpers, and blast radius.
7. **Merge.** Sprint PR → integration branch follows the project's merge setting (`user` or `agent`). Merge requires: all non-stuck issues merged, verification passed or its remaining rows handed to the user, sprint review approved, green CI. Issues close via their `Closes #N`; the milestone closes when all its issues are closed.
8. **Report.** Done issues, stuck issues with reasons, evidence, and the user checks still open.

Resume: read the milestone, labels, sprint branch, and sprint PR; continue with the next unfinished issue.

## 8. Project planning (`skills/plan-project`)

- **Create mode:** interview the user about the product; write the PRD issue with requirement IDs; split work into milestones and issues (each issue lists its requirement IDs, acceptance tests in plain words, and "Blocked by" links); add one verification issue per milestone. Show the full list before creating anything.
- **Update mode:** a new idea or change is written into the PRD issue with new or revised requirement IDs, then turned into issues added to an open milestone or a new one. Show the diff before writing.

## 9. Tracker mapping (GitHub first)

| Concept | GitHub |
|---|---|
| PRD | Pinned `PRD` issue (or wiki), requirement IDs inside |
| Sprint | Milestone + `sprint/<milestone>` branch + draft sprint PR |
| Ticket | Issue with `type:*` and `area:*` labels |
| Dependency | "Blocked by #N" in the body |
| Status | `status:in-progress`, `status:needs-input`, `status:blocked`, `status:in-review` |
| Plan | One plan comment, edited in place |
| Done | Closed via merged PR `Closes #N` |
| User checks | Checkbox list in the issue or verification issue |

`tracker/github.md` lists the exact `gh` command per action. Another tracker = another file with the same action list.

## 10. Safety baseline (`safety/baseline.md`)

Never: force push, rewrite history, `git reset`/`stash`/`clean`/`checkout --`, delete branches or repos, `sudo`, `rm -rf`, edit or read `.env`/secrets, add/upgrade/remove packages unless a plan step says so, close issues by hand, merge into the integration branch unless `merge: agent` and all merge conditions hold (merging an approved issue PR into its sprint branch is always allowed). Tracker writes only through `tracker/github.md` commands.

Role permissions: scout and pr-reviewer read-only; test-writer edits tests only; coder never edits tests; delivery is the only role that pushes or opens PRs. Each worker has a step limit and the same-error retry limit; hitting either returns to the planner with attempts listed.

Projects add rules in `AGENTS.md` and `forbiddenCommands`. Adapters translate baseline + project rules into the tool's permission config once, not per agent.

## 11. Testing the kit

- `examples/sandbox/` plus a release checklist: run setup, run one feature issue and one bug-fix issue, then a two-issue sprint, confirm labels, plan comment, PR, review, evidence, merge behavior.
- Dry run on a real existing project before each release (report changes, write nothing).
- `VERSION` + `CHANGELOG.md` so `UPDATE.md` can show what changed.

## 12. Adopting the kit in an existing project

- Existing hard rules in `AGENTS.md` (or similar) become project rules; commands agents must not run go in `forbiddenCommands`.
- Existing tool-specific agent and skill files are replaced by adapter output, after a diff the user approves.
- File-based ticket tracking (sprint folders, timelines, status sections) stops being the source of truth; open tickets become issues under milestones.
- Unused or unknown tooling is listed for the user to keep or remove; setup never deletes it on its own.

## 13. Decisions made

- Tool and model agnostic; choices recorded per project at setup.
- Kit = markdown followed by an agent (no installer program).
- Copy-once with explicit, diffed updates.
- State in the tracker; plan as an issue comment; PR body summarizes and links it.
- Two run modes: `run-issue` (user pastes an issue) and `run-sprint` (user names a milestone; issues run in dependency order on a sprint branch).
- `plan-project` creates the PRD, milestones and issues, and updates them later.
- Independent PR reviewer agent.
- Merge policy is a per-project setting (`user` or `agent`) for PRs into the integration branch; issue PRs inside a sprint are always merged into the sprint branch by the agent.
- Repo name `agentic-workflow-kit`, public. Kit files contain no personal or project-specific data.

## 14. Facts found while building 0.1.0

- **Closing issues:** GitHub's `Closes #N` only works when a PR merges into the default branch. When the integration branch isn't the default branch, delivery closes the issue directly after confirming the merge. This is the single allowed hand-close (see `tracker/github.md`).
- **Own-PR approval:** GitHub rejects approving a PR from the account that opened it. The reviewer falls back to a comment review whose first line is `<!-- agentkit:review verdict=… sha=… -->`, and that marker counts as the review.
- **Sprint draft PR:** GitHub refuses a PR with no commits, so the sprint branch starts with an empty commit.
- **No CI:** when a repo has no CI, the check command's result on the PR head commit in the evidence section stands in for green CI.
- **Claude Code:** subagents can't start subagents, so the planner runs as the main session through the `run-issue` and `run-sprint` skills. Per-role edit limits that the tool can't express are enforced by role instructions and re-checked by the pr-reviewer.
- **Updates:** `installedFiles` in the lock file records a sha256 per written file, so `UPDATE.md` can tell kit-generated content from the user's edits.
- **Kit test:** `scripts/check-kit.sh` checks required files, skill frontmatter, tool or model names in generic files, placeholders, and links.
